# MVP scoping guide

## What an MVP is
A minimum viable product is the smallest version of a product that lets you test the most important assumption with real users. It is not a low-quality product; it is a focused one.

## Steps to scope an MVP
1. **List assumptions** about the customer, the problem, and the solution.
2. **Choose the riskiest assumption** (the one that would end the idea if wrong).
3. **Define one core user journey** that tests it, from first contact to the main value.
4. **List possible features**, then cut everything that is not needed for that journey.
5. **Decide the success metric** before building (for example number of completed bookings in two weeks).

## MoSCoW prioritisation
- **Must have:** the product fails without it.
- **Should have:** important but a workaround exists.
- **Could have:** nice to have if time allows.
- **Won't have (now):** explicitly postponed.
A first release usually contains only Must-have items.

## Types of MVP
- **Landing page:** tests interest before building anything.
- **Concierge:** the service is delivered manually to a few customers.
- **Wizard of Oz:** the interface looks automated but people operate it behind the scenes.
- **Single-feature product:** one feature done well.
- **Prototype or clickable mock-up:** tests usability and understanding.

## Common mistakes
- Building many features before talking to users.
- Treating all requests as equally important.
- Measuring vanity metrics (page views) instead of behaviour (repeat use, payment).
- Having no clear end date or decision rule for the test.

## For software projects
Pick a small technology stack the team already knows, build the core flow end-to-end first, add authentication and data storage early, and defer integrations, advanced analytics, and automation until the core flow is used.
